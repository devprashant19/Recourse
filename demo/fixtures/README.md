# demo/fixtures

Recorded NEAR AI Cloud interactions that make the sandbox demo **keyless**. The fixture twin changes
where the bytes come from, **not whether they are checked**: every replayed response still goes
through EIP-191 signer recovery, request/response hash matching and the TDX `report_data`
nonce/signer binding.

| Set | Kind | What it is |
|---|---|---|
| `near-ai/fixtures.json` | `genuine` | Recorded from NEAR AI Cloud on 8 Nov 2026 by `pnpm record-fixtures --live`: worker `Qwen/Qwen3.8-27B` (TEE signer `0x835ab53d…aa26`), arbiter `z-ai/glm-5.3-flash` (TEE signer `0x3b753b44…fa0c`). Every TDX quote was verified by dcap-qvl at recording time (all `UpToDate`). **The sandbox uses this set** whenever it is present. |
| `dev/fixtures.json` | `dev` | Fallback when `near-ai/` is absent. **Not NEAR AI Cloud output.** Generated by `pnpm record-fixtures --dev`: answers computed from ground truth, signed by a throwaway key derived from the public label `recourse/test-vector/tee`, quotes with no Intel signature. Receipts built on it say `dev-fixture: no Intel signature, no TEE` in `attestation.verifier`. Sandbox only. |

`plan.ts` lists what is recorded: correct extractions of all five documents (the judge's five
receipts), scenario 02's `wrong_total` extraction, and the arbiter verdicts for scenarios 02 and 04.
Requests are built by the worker's and arbiter's own request builders, so they are byte-identical to
what the services send.

A recorded attestation report binds the nonce sent when it was recorded, so replay reuses that nonce;
fresh-nonce attestation is exercised only in live (testnet/mainnet) mode.

```bash
pnpm record-fixtures --live            # needs NEARAI_API_KEY, NEARAI_MODEL_WORKER, NEARAI_MODEL_ARBITER
pnpm record-fixtures --dev --force     # regenerate the dev set
```
Both replay and verify every receipt before writing, and refuse to overwrite without `--force`.

With the genuine set present, setup allow-lists its two real TEE signers (each with the sha256 of the
attestation report Intel verified) alongside the dev key. Scenarios 01, 02 and 04 run the real worker and
arbiter, so their receipts and verdicts are the NEAR AI Cloud recordings. Scenarios 05–07 and the
adversarial suite still sign synthetic receipts with the dev key: they test the contract's money and
market mechanics, not the model.
